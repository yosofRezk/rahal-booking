## 2. الفكرة والنطاق

البلاجن **Booking Engine مستقل**: بياخد رحلات موجودة بالفعل في الموقع (أيًّا كان نظامها) ويضيف عليها حجز كامل.

```text
Tour موجود بالفعل  →  البلاجن بيربطه بالحجز  →  العميل يحجز
→ النظام يتأكد من المقاعد ويحسب السعر  →  الحجز يتسجل برقم مرجعي
→ الأدمن يدير الحالة  →  إيميلات
```

**Tour = المنتج. Booking = عملية الشراء.**

### ليه البلاجن مش بينشئ رحلات في النسخ الأولى؟

لأن كل موقع بيعرض رحلاته بطريقة مختلفة:

| الموقع | نوع المحتوى | حقل المقاعد | حقل السعر |
| --- | --- | --- | --- |
| Rahal | `tours` | `total_seats` | `tour_price` |
| Nile Trips | `trip` | `capacity` | `price` |
| Sinai Camps | `packages` | `max_people` | `cost` |

لو البلاجن فرض Tour CPT بتاعه، صاحب الموقع لازم ينقل كل رحلاته. بالشكل ده البلاجن يتركّب على أي موقع في دقايق.

### الخطة الأبعد

في **v2.0 من البلاجن** (مش من الوثيقة) هيبقى فيه خيار إنشاء الرحلات من جوه البلاجن للمواقع الجديدة، مع استمرار دعم الربط بأي نظام موجود.

## 3. القرار 1: جدول مخصص للحجوزات بدل CPT

### المشكلة

رحلة باريس فيها 10 مقاعد والمتاح 2. عميلين يضغطوا «احجز» في نفس الثانية، كل واحد عايز مقعدين.

لو الحجز بيتم بـ CPT + Meta، الطلب بيعمل 3 خطوات منفصلة:

1. يحسب المتاح (بـ `meta_query` يجمع عدد الأفراد من كل الحجوزات).
2. يعمل Post جديد.
3. يكتب الـ Meta بتاعته.

الخطوات دي **مش ذرّية (atomic)**: الطلب التاني ممكن يعدّي الخطوة 1 قبل ما الأول يوصل للخطوة 3، فالاتنين يشوفوا «متاح 2» والاتنين يحجزوا.

ومشكلة تانية هي السرعة: كل حجز CPT بيخزّن حوالي 15 صف في `wp_postmeta`. لو عندك 5000 حجز يبقى 75 ألف صف، و`meta_query` بتعمل JOIN على كل شرط. حساب المقاعد هيبقى بطيء وهو بيظهر في كل صفحة رحلة.

### الحل

جدول واحد للحجوزات، فيه Index على اللي بنسأل عنه كتير، وحساب المقاعد بيبقى استعلام واحد سريع.

### شكل الجدول

```sql
CREATE TABLE wp_tbs_bookings (
  id                    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  reference             VARCHAR(32)  NOT NULL DEFAULT '',
  tour_id               BIGINT UNSIGNED NOT NULL,
  tour_date             DATE NULL,
  guests                SMALLINT UNSIGNED NOT NULL,
  customer_name         VARCHAR(190) NOT NULL,
  customer_email        VARCHAR(190) NOT NULL,
  customer_phone        VARCHAR(40)  NOT NULL,
  currency              CHAR(3)      NOT NULL,
  price_per_guest_minor BIGINT NOT NULL,
  subtotal_minor        BIGINT NOT NULL,
  discount_minor        BIGINT NOT NULL DEFAULT 0,
  total_minor           BIGINT NOT NULL,
  booking_status        VARCHAR(20)  NOT NULL DEFAULT 'pending',
  payment_status        VARCHAR(20)  NOT NULL DEFAULT 'unpaid',
  payment_method        VARCHAR(30)  NOT NULL DEFAULT '',
  transaction_id        VARCHAR(100) NOT NULL DEFAULT '',
  tour_title_snapshot   VARCHAR(255) NOT NULL DEFAULT '',
  expires_at            DATETIME NULL,
  created_at            DATETIME NOT NULL,
  updated_at            DATETIME NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY reference (reference),
  KEY tour_seats (tour_id, tour_date, booking_status, expires_at),
  KEY customer_email (customer_email)
);
```

**ملاحظات تنفيذ:**

- الاسم الحقيقي بيبقى `$wpdb->prefix . 'tbs_bookings'` (البريفكس مش دايمًا `wp_`).
- الجدول بيتنشأ وقت التفعيل بدالة `dbDelta()` الخاصة بووردبريس.
- بنخزّن رقم نسخة قاعدة البيانات في option اسمه `tbs_db_version` عشان لو أضفنا أعمدة في نسخ جاية نعمل Migration.
- كل التواريخ بتتخزن بتوقيت UTC.

### مثال على الصفوف

| id | reference | tour\_id | tour\_date | guests | booking\_status | expires\_at |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | TB-2026-00001 | 892 | 2026-12-10 | 4 | confirmed | NULL |
| 2 | TB-2026-00002 | 892 | 2026-12-10 | 6 | pending | 2026-10-09 10:15 |
| 3 | TB-2026-00003 | 892 | 2026-12-10 | 3 | cancelled | NULL |
| 4 | TB-2026-00004 | 892 | 2026-12-20 | 5 | confirmed | NULL |

### حساب المقاعد

```sql
SELECT COALESCE(SUM(guests), 0)
FROM wp_tbs_bookings
WHERE tour_id = 892
  AND tour_date = '2026-12-10'
  AND (
        booking_status = 'confirmed'
     OR (booking_status = 'pending' AND expires_at > UTC_TIMESTAMP())
      );
```

على الصفوف اللي فوق، والساعة قبل 10:15:

- محجوز يوم 10 ديسمبر = 4 + 6 = **10** (الحجز رقم 3 ملغي فمش بيتحسب).
- لو إجمالي المقاعد 20، يبقى المتاح = **10**.
- يوم 20 ديسمبر محجوز **5**، والمتاح **15**.

لاحظ شرط `expires_at`: الحجز المعلق بعد انتهاء مهلته **مش بيتحسب حتى لو لسه حالته Pending في الجدول**. يعني مقاعده بترجع متاحة فورًا من غير ما نستنى الـ Cron.

### إيه اللي بنخسره؟

مع CPT كنا بنحصل مجانًا على شاشة إدارة جاهزة (بحث، فلاتر، صلاحيات). مع الجدول المخصص لازم نبني شاشة الأدمن بـ `WP_List_Table` (كلاس جاهز من ووردبريس). الـ AI بيعرف يكتبها، والمقابل إننا ضمنّا الأمان والسرعة.

## 4. القرار 2: منع الحجز المزدوج من أول نسخة

كان في v1.0 ضمن «مرحلة متقدمة». دلوقتي هو **جزء من v0.1** لأن إضافته بعد ما بيانات حقيقية تتسجل مؤلمة.

### السيناريو من غير حماية

```text
رحلة: 10 مقاعد، المتاح 2

10:00:00.000  عميل A: كام متاح؟    ← 2
10:00:00.010  عميل B: كام متاح؟    ← 2
10:00:00.050  عميل A: يحجز 2        ← محجوز 10 من 10
10:00:00.060  عميل B: يحجز 2        ← محجوز 12 من 10  ❌
```

### السيناريو مع قفل (Lock)

```text
عميل A: يطلب القفل          ← ياخده
عميل B: يطلب القفل          ← يستنى
عميل A: يحسب المتاح (2) ← يحجز 2 ← يفك القفل
عميل B: ياخد القفل ← يحسب المتاح (0) ← يرفض:
        'Sorry, only 0 seats are available.'
```

### الكود المبدئي

```php
function tbs_create_booking( $tour_id, $tour_date, $guests, $data ) {
    global $wpdb;

    $lock_name = 'tbs_' . $tour_id . '_' . $tour_date; // أقل من 64 حرف
    $got_lock  = $wpdb->get_var(
        $wpdb->prepare( 'SELECT GET_LOCK(%s, 5)', $lock_name )
    );

    if ( ! $got_lock ) {
        return new WP_Error( 'busy', 'Please try again in a moment.' );
    }

    try {
        $available = tbs_get_available_seats( $tour_id, $tour_date );

        if ( $guests > $available ) {
            return new WP_Error(
                'no_seats',
                sprintf( 'Sorry, only %d seats are available.', $available )
            );
        }

        // هنا بنعمل INSERT للحجز
        $wpdb->insert( $wpdb->prefix . 'tbs_bookings', $row );
        return $wpdb->insert_id;

    } finally {
        $wpdb->query(
            $wpdb->prepare( 'SELECT RELEASE_LOCK(%s)', $lock_name )
        );
    }
}
```

### قواعد مهمة

- القفل **لكل رحلة + تاريخ**، فحجز رحلة مش بيعطّل رحلة تانية.
- أقصى انتظار 5 ثواني.
- فك القفل لازم يبقى في `finally` عشان لو حصل خطأ ما يفضلش القفل معلّق.
- ده بديل بسيط للمبتدئين. البديل الأقوى هو `START TRANSACTION` مع `SELECT ... FOR UPDATE` على صف الرحلة، وممكن نرقّي له لاحقًا.
- **شبكة أمان تانية:** بعد الـ INSERT نعيد الحساب، ولو الإجمالي عدّى سعة الرحلة نلغي الحجز ونرجّع خطأ.

## 5. القرار 3: أي حالة بتحجز مقاعد (وحل تعارض Completed)

في v1.0 قلنا إن Completed مش بتحجز مقاعد، لكن Completed بتعني الرحلة خلصت، فكان فيه لبس.

### القاعدة الجديدة (جملة واحدة)

> الحجز بيحجز مقاعد لو حالته **confirmed**، أو **pending** ومهلته (`expires_at`) لسه ما عدّتش.

| الحالة | بتحجز مقاعد؟ | الشرح |
| --- | --- | --- |
| pending | أيوه، لحد `expires_at` | حجز مؤقت مستني الدفع أو التأكيد |
| confirmed | أيوه | حجز مؤكد |
| completed | لا | الرحلة عدّت، والبلاجن يمنع الحجز في تاريخ فات، فمحدش بيتأثر |
| rejected | لا | الأدمن رفضه |
| cancelled | لا | اتلغى |
| expired | لا | المهلة خلصت |

### قاعدة Completed

الأدمن **ما يقدرش** يعلّم حجز Completed إلا بعد `tour_date`.

**مثال:** حجز رحلة 10 ديسمبر. لو الأدمن حاول يعمل Completed يوم 5 ديسمبر، البلاجن يرفض ويقول «الرحلة لسه ما بدأتش».

### الانتقالات المسموحة

```text
pending ──► confirmed ──► completed   (بعد تاريخ الرحلة فقط)
   │            │
   │            └──────► cancelled
   ├──────────► rejected
   ├──────────► cancelled
   └──────────► expired   (تلقائي)
```

- `completed` و `rejected` و `expired` حالات نهائية، مفيش رجوع منها.
- أي انتقال مش في الرسم ده بيترفض بالكود (مثلًا من `expired` إلى `confirmed`).

## 7. القرار 5: الرقم المرجعي

### المشكلة

لو الكود بيعمل «هات آخر رقم وزوّد 1»:

```text
عميل A: آخر رقم 16  ← يعمل 17
عميل B: آخر رقم 16  ← يعمل 17     ❌ نفس الرقم
```

### الحل

نستعمل الـ `AUTO_INCREMENT` بتاع الجدول لأن قاعدة البيانات هي اللي بتضمن إنه ما يتكررش:

```php
$wpdb->insert( $table, $row );              // reference فاضي مؤقتًا
$id        = $wpdb->insert_id;              // مثلًا 17
$reference = sprintf( 'TB-%s-%05d', gmdate( 'Y' ), $id );  // TB-2026-00017
$wpdb->update( $table, array( 'reference' => $reference ), array( 'id' => $id ) );
```

والعمود `reference` فيه `UNIQUE KEY` كحماية إضافية.

### نقطة أمان

الأرقام المتسلسلة سهل تخمينها. فلو عميل بيعرض حجزه من الموقع، لازم يدخل **الرقم المرجعي + الإيميل** مع بعض، عشان محدش يجرّب أرقام ويشوف حجوزات غيره.

## 8. القرار 6: الفلوس أرقام صحيحة

### المشكلة

الأرقام العشرية في البرمجة بتغلط:

```text
0.1 + 0.2 = 0.30000000000000004
```

في فلوس الناس ده غير مقبول.

### الحل

نخزّن المبالغ **بأصغر وحدة للعملة** كأرقام صحيحة، ومعاها كود العملة:

| المبلغ الحقيقي | بيتخزّن |
| --- | --- |
| $760.00 | `76000` + `USD` |
| 450.50 جنيه | `45050` + `EGP` |
| $200.00 سعر الفرد | `20000` |

### مثال حساب كامل بخصم 5%

```text
سعر الفرد  = 20000    ($200.00)
عدد الأفراد = 4
Subtotal   = 20000 × 4 = 80000      ($800.00)
Discount   = 80000 × 5 / 100 = 4000 ($40.00)
Total      = 80000 − 4000 = 76000   ($760.00)
```

### قاعدة التقريب

لو الخصم طلع كسر نقرّبه لأقرب وحدة صحيحة (نصف لأعلى):

```php
$discount = intdiv( $subtotal * $percent + 50, 100 );
// مثال: 33333 × 5% = 1666.65 → 1667
```

### العرض للمستخدم

`number_format( $minor / 100, 2 )` → `760.00`، وبنضيف رمز العملة حسب الإعدادات.

**ملاحظة:** في v0.1 بنفترض إن العملة بتاعتها خانتين عشريتين (USD, EGP, EUR). العملات اللي من غير كسور (زي الين الياباني) نضيفها بعدين.

## 9. القرار 7: انتهاء الحجز المعلّق + الحماية من الحجوزات الوهمية

### المشكلة

بوت يعمل 5 حجوزات × 4 أفراد على رحلة فيها 20 مقعد ← الرحلة تظهر Sold out وإنت ما بعتش حاجة. وفي المقابل، عميل حقيقي اختار الدفع في الفرع ممكن يوصل بعد يومين، فمهلة 15 دقيقة ظالمة ليه.

### مهلة الحجز حسب طريقة الدفع

| طريقة الدفع | المهلة المقترحة | السبب |
| --- | --- | --- |
| Online (من v1.0) | 15 دقيقة | العميل بيدفع فورًا |
| Pay at Branch | 48 ساعة | ممكن يزور الفرع بعد يومين |
| Manual Transfer | 24 ساعة | وقت التحويل البنكي |

الأرقام دي كلها قابلة للتعديل من Settings، ومحفوظة في `expires_at` لكل حجز وقت إنشائه.

### مثال كامل

```text
الخميس 10:00  عميل يحجز 4 أفراد، دفع في الفرع
              → pending + expires_at = السبت 10:00

الجمعة 15:00  العميل دفع والأدمن أكّد
              → confirmed + expires_at = NULL   (المقاعد محجوزة نهائي)

-- أو لو محدش أكّد --

السبت 10:00   المهلة خلصت
              → المقاعد ترجع متاحة فورًا (استعلام العدّ بيتجاهل المنتهي)
السبت 10:30   الـ Cron يحوّل الحالة لـ expired ويبعت إيميل للعميل
```

### الـ Cron (تنضيف الحالة)

```php
register_activation_hook( __FILE__, function () {
    if ( ! wp_next_scheduled( 'tbs_expire_bookings' ) ) {
        wp_schedule_event( time(), 'hourly', 'tbs_expire_bookings' );
    }
} );

add_action( 'tbs_expire_bookings', function () {
    global $wpdb;
    $t = $wpdb->prefix . 'tbs_bookings';
    $wpdb->query(
        "UPDATE $t SET booking_status = 'expired'
         WHERE booking_status = 'pending' AND expires_at <= UTC_TIMESTAMP()"
    );
} );
```

**مهم:** الـ Cron مجرد تنضيف للحالة وإرسال الإيميل. صحة عدد المقاعد مش معتمدة عليه لأن استعلام الحساب بيتجاهل المنتهي لوحده (قسم 3).

### الحماية من الحجوزات الوهمية

| الحماية | بتعمل إيه | النسخة |
| --- | --- | --- |
| Honeypot | حقل مخفي، لو اتملا يبقى بوت والطلب يترفض | v0.1 |
| حد أقصى للأفراد في الحجز | افتراضي 10 أفراد في الحجز الواحد | v0.1 |
| Rate Limit بالـ IP | 5 محاولات في الساعة | v0.1 |
| حد للحجوزات المعلقة | حجزين pending بس لنفس الإيميل ونفس الرحلة والتاريخ | v0.1 |
| CAPTCHA اختياري | Cloudflare Turnstile أو reCAPTCHA | v0.2 |

```php
$key   = 'tbs_rl_' . md5( $ip . wp_salt() );   // الـ IP متشفّر، مش بنخزّنه صريح
$count = (int) get_transient( $key );

if ( $count >= 5 ) {
    return new WP_Error( 'rate_limited', 'Too many attempts. Please try again later.' );
}
set_transient( $key, $count + 1, HOUR_IN_SECONDS );
```

## 10. ربط الرحلات والإعدادات (Tour Integration)

البلاجن ما يعرفش أسماء الحقول عندك، فصاحب الموقع يعرّفه بيها مرة واحدة من Settings.

| الإعداد | معناه | مثال Rahal | مثال Nile Trips |
| --- | --- | --- | --- |
| Tour Post Type | نوع المحتوى بتاع الرحلات | `tours` | `trip` |
| Seats Field | حقل عدد المقاعد | `total_seats` | `capacity` |
| Price Field | حقل سعر الفرد | `tour_price` | `price` |
| Date Field | حقل تاريخ الرحلة (اختياري) | `starting_date` | `trip_date` |
| Currency | العملة | `USD` | `EGP` |

القراءة بتتم من الـ Post Meta مباشرة:

```php
$seats = (int) get_post_meta( $tour_id, $settings['seats_field'], true );
```

ACF بيحفظ في الـ Post Meta العادي، فالبلاجن بيشتغل معاه من غير ما يعتمد عليه. كمان بيشتغل مع Meta Box أو أي Custom Fields.

### حالات لازم نتعامل معاها

| الحالة | المشكلة | الحل |
| --- | --- | --- |
| تاريخ ACF | ACF Date Picker بيخزّن `20261210` مش `2026-12-10` | نحوّله لصيغة `Y-m-d` قبل الحفظ |
| سعر مكتوب بشكل مختلف | `$200` أو `1,200.50` | ننضّف الحروف والفواصل ونحوله لأصغر وحدة (قسم 8) |
| مقاعد فاضية أو 0 | ممكن تتفهم إنها مقاعد لا نهائية | الرحلة تعتبر مش متاحة، والفورم يتخبّى ويظهر Not available |
| حقل مش موجود | الأدمن كتب اسم غلط | إشعار في الأدمن: Seats field total\_seats not found on tour 892 |
| تغيير الرحلة بعد الحجز | الاسم أو السعر اتغير | الحجز القديم محتفظ بـ `tour_title_snapshot` والأسعار وقت الحجز |

- اقتراح أسماء الحقول من رحلة موجودة (قراءة الـ meta keys بتاعتها).

## 11. التسعير (Pricing)

### v0.1: سعر الفرد × عدد الأفراد

```php
// class-pricing.php
function tbs_calculate_price( $tour_id, $guests ) {
    $price_per_guest = TBS_Tour::get_price_minor( $tour_id );   // مثلا 20000
    $subtotal        = $price_per_guest * $guests;              // 80000
    $discount        = 0;                                       // v0.1 بدون خصومات

    return array(
        'currency'              => TBS_Settings::get( 'currency' ),
        'price_per_guest_minor' => $price_per_guest,
        'subtotal_minor'        => $subtotal,
        'discount_minor'        => $discount,
        'total_minor'           => $subtotal - $discount,
    );
}
```

الدالة دي بتتنادى **على السيرفر** وقت الحجز. الرقم اللي بيظهر للعميل في JavaScript مجرد عرض، والسيرفر بيعيد الحساب بنفسه.

**مثال هجوم:** حد يعدّل الصفحة ويبعت `total=100` بدل 760. الكود يتجاهل أي سعر جاي من الفورم، ويحسب من سعر الرحلة الموجود في قاعدة البيانات.

### v0.3: قواعد الخصم

| القاعدة | مثال |
| --- | --- |
| خصم جروب | 4 أفراد فأكتر = 5% |
| Early Booking | الحجز قبل الرحلة بـ 30 يوم = 10% |
| سعر الأطفال | Adult = $200, Child = $120, Infant = Free |
| كوبون | SUMMER20 |

**قاعدة التطبيق: الخصومات مش بتتجمّع، بيتطبق الأكبر بس.**

مثال: حجز 4 أفراد × $200 = $800، وقبل الرحلة بـ 40 يوم:

```text
خصم الجروب (5%)          = $40
خصم الحجز المبكر (10%)   = $80   ← الأكبر
المطبّق                    = $80
Total                     = $720
```

ولو عايز تسمح بالتجميع بعدين، يبقى خيار في Settings.

كل الأسعار النهائية بتعدّي على الفلتر:

```php
$total = apply_filters( 'tbs_booking_total', $total, $booking_data );
```

## 12. الدفع (Payments)

### v0.1: دفع يدوي بس

| الطريقة | الحالة بعد الحجز | مين يغيّرها |
| --- | --- | --- |
| Pay at Branch | Pending / Unpaid | الأدمن بعد استلام الفلوس |
| Manual Transfer | Pending / Unpaid | الأدمن بعد مراجعة التحويل |

تعليمات الدفع (عنوان الفرع أو رقم الحساب) بتتكتب في Settings وبتظهر بعد الحجز وفي الإيميل.

### حالات الدفع

| الحالة | معناها |
| --- | --- |
| unpaid | لسه ما دفعش |
| pending | عملية دفع بدأت ومستنيين النتيجة (أونلاين) |
| paid | تم الدفع |
| failed | الدفع فشل |
| refunded | تم الاسترجاع |

### الدفع الأونلاين (بعد v1.0): الطبقة العامة

الـ Core ما يتكلمش مع Stripe أو Paymob مباشرة، بل مع Interface:

```php
interface TBS_Gateway {
    public function get_id(): string;
    public function create_payment( array $booking ): array;      // يرجّع رابط الدفع
    public function handle_webhook( WP_REST_Request $request );   // يستقبل تأكيد البوابة
}
```

كل بوابة (Stripe، Paymob، PayPal) تبقى ملف مستقل يطبّق الـ Interface.

### مسار الـ Webhook خطوة بخطوة

1. البوابة تبعت طلب على `/wp-json/tbs/v1/webhook/paymob`.
2. نتحقق من **التوقيع (Signature/HMAC)** عشان نتأكد إنه من البوابة فعلًا، مش من حد منتحل.
3. نلاقي الحجز بالـ `transaction_id` أو الـ reference.
4. نقارن **المبلغ والعملة** اللي البوابة بتقول عليهم مع `total_minor` و`currency` المخزّنين.
5. نتأكد إننا ما عالجناش نفس العملية قبل كده (**Idempotency**)، لأن البوابات ممكن تبعت نفس الـ Webhook مرتين.
6. لو كله سليم: `payment_status = paid` و `booking_status = confirmed` ونبعت إيميل التأكيد.

### حالات صعبة

| الحالة | القرار |
| --- | --- |
| المبلغ المدفوع غير مطابق | ما نأكّدش الحجز. `payment_status = pending` وتنبيه للأدمن |
| نفس الـ Webhook وصل مرتين | الطلب التاني يتتجاهل (الحجز already paid) |
| الدفع وصل بعد انتهاء مهلة الحجز | لو المقاعد لسه متاحة نأكّد الحجز. لو اتحجزت لحد تاني: الحجز يتعلّم Needs Refund وتنبيه للأدمن |
| العميل رجع بالـ Return URL من غير Webhook | الصفحة بتعرض Payment processing وما نغيّرش الحالة |

## 13. لوحة الأدمن والإيميلات

### قائمة الأدمن

```text
Travel Bookings
├── All Bookings      (جدول بكل الحجوزات + فلاتر وبحث)
└── Settings          (الربط والمهل والإيميلات والدفع)
```

جدول الحجوزات مبني بـ `WP_List_Table`، وفيه:

| العمود | مثال |
| --- | --- |
| Reference | TB-2026-00022 |
| Customer | Ahmed Ali (ahmed@example.com) |
| Tour + Date | Paris Discovery — 10 Dec 2026 |
| Guests | 4 |
| Total | $760.00 |
| Payment | Unpaid |
| Status | Pending |

**الفلاتر:** حالة الحجز، حالة الدفع، الرحلة، التاريخ. **البحث:** بالرقم المرجعي أو الاسم أو الإيميل أو التليفون.

### إجراءات الأدمن

| الإجراء | بيعمل إيه | قيد |
| --- | --- | --- |
| Confirm | pending ← confirmed | بيعرض خيار Mark as Paid في نفس الخطوة |
| Reject | pending ← rejected | إيميل للعميل |
| Cancel | pending أو confirmed ← cancelled | المقاعد ترجع متاحة تلقائيًا |
| Complete | confirmed ← completed | بعد تاريخ الرحلة فقط (قسم 5) |
| Mark as Paid | payment\_status ← paid | للدفع اليدوي |

**مثال Pay at Branch:** العميل وصل الفرع وقال TB-2026-00022. الموظف يكتب الرقم في البحث، يفتح الحجز، ويدوس Confirm مع Mark as Paid. الحالتين يتغيروا مرة واحدة، والعميل يستلم إيميل تأكيد.

**كل إجراء بيعدّي على:** فحص Nonce + فحص صلاحية `tbs_manage_bookings` (صلاحية بنضيفها للأدمن وقت التفعيل) + فحص إن الانتقال مسموح (قسم 5).

### الإيميلات

| الحدث | المستلم | النسخة |
| --- | --- | --- |
| Booking Received | العميل | v0.1 |
| New Booking | الأدمن | v0.1 |
| Booking Confirmed | العميل | v0.2 |
| Booking Rejected / Cancelled | العميل | v0.2 |
| Booking Expired | العميل | v0.2 |
| Payment Received | العميل | v1.0 |

**شكل إيميل Booking Received:**

```text
مرحبًا {customer_name}،

استلمنا حجزك.

رقم الحجز:  {reference}
الرحلة:      {tour_title}
التاريخ:     {tour_date}
عدد الأفراد: {guests}
الإجمالي:    {total}
الحالة:      Pending

{payment_instructions}
```

**قواعد الإيميلات:**

- بنستخدم `wp_mail()`. فشل الإرسال **لا يلغي الحجز**، بيتسجل في اللوج بس.
- كتير من الاستضافات الإيميلات بتاعتها بتروح Spam، فبننصح في التوثيق بتركيب بلاجن SMTP.
- القوالب تقبل الاستبدال من الثيم لاحقًا (v0.4).

```php
add_action( 'tbs_booking_confirmed', function ( $booking_id ) {
```

### الكاش (قاعدة مهمة)

- **العرض** (رقم المقاعد في صفحة الرحلة أو الأرشيف) ممكن يتخزّن 30 ثانية في Transient.

يعني ممكن العميل يشوف 5 متاح وهي فعليًا 4، لكن الحجز نفسه ما يعدّيش غير لو فعلًا متاح.

## 15. الأمان

| التهديد | الحماية | مثال |
| --- | --- | --- |
| طلب مزوّر على الفورم | Nonce | `wp_nonce_field()` و`wp_verify_nonce()` |
| مستخدم عادي ينفّذ إجراء أدمن | فحص الصلاحية | `current_user_can( 'tbs_manage_bookings' )` |
| مدخلات ضارة | Sanitize | `sanitize_text_field()`, `sanitize_email()`, `absint()` |
| بيانات غلط | Validation | `is_email()`, عدد الأفراد بين 1 وأقصى حد، التاريخ مش في الماضي |
| XSS في العرض | Escape | `esc_html()`, `esc_attr()`, `esc_url()` |
| SQL Injection | Prepared Queries | `$wpdb->prepare()` في كل استعلام فيه متغير |
| تلاعب بالسعر | حساب على السيرفر | قسم 11 |
| حجز أكتر من المتاح | تحقق على السيرفر + قفل | قسم 4 |
| Webhook مزوّر | فحص التوقيع | قسم 12 |
| فتح الملف مباشرة | حارس في أول كل ملف PHP | \`defined( 'ABSPATH' ) |
| سرقة بيانات عميل | الرقم المرجعي + الإيميل معًا للاستعلام | قسم 7 |

**مشكلة عملية: الكاش وNonce.** بلاجنات الكاش بتخزّن الصفحة بما فيها الـ Nonce، فبعد ساعات الفورم يفشل. الحل: الفورم يجيب Nonce جديد وقت تحميل الصفحة عن طريق REST، وحماية Honeypot وRate Limit تفضل شغالة كخط دفاع تاني.

**الخصوصية:** بيانات العملاء (اسم، إيميل، تليفون) بيانات شخصية. في v0.4 نضيف Exporter وEraser متوافقين مع أدوات الخصوصية في ووردبريس. والـ Logs ما تسجّلش بيانات حساسة.

**عند حذف البلاجن:** `uninstall.php` ما يمسحش جدول الحجوزات إلا لو صاحب الموقع اختار ده صراحة في Settings (مسح الحجوزات بالغلط كارثة).

## 19. قواعد البناء بالـ AI

المشروع هيتبني بمساعدة AI، وده معناه إن مسؤوليتك تتحول من كتابة الكود لـ **توجيه ومراجعة واختبار**.

### قواعد الجلسات

1. **حط الوثيقة دي في المشروع** (ملف `docs/SPEC.md`) وابدأ كل جلسة بـ: اقرأ SPEC.md وهنشتغل على الخطوة رقم X.
2. **مهمة واحدة في الرسالة.** مش نبني الأدمن والفورم والإيميلات مع بعض.
3. **اختبر قبل ما تكمّل.** كل خطوة ليها اختبار في قسم 18.
4. **Commit بعد كل خطوة شغالة** على Git. لو الـ AI بوّظ حاجة، ترجع لآخر نسخة سليمة.
5. **ما تسيبش الـ AI يضيف ميزات برّه النسخة.** لو اقترح، اكتبها في قايمة أفكار وكمّل.
6. **لما يحصل خطأ:** ابعت رسالة الخطأ كاملة + الملف المعني. مش بس: مش شغال.
7. **اطلب الشرح** في الأجزاء الحساسة (القفل، الأمان، الـ Webhook) لحد ما تفهمها، لأنك المسؤول عنها قدام المستخدمين.

### مثال Prompt جيد وآخر سيئ

| سيئ | جيد |
| --- | --- |
| اعملي بلاجن حجز كامل | اقرأ SPEC.md. هنعمل الخطوة 2 بس: class-installer.php اللي بينشئ جدول tbs\_bookings بالأعمدة الموجودة في قسم 3 باستخدام dbDelta، ويخزّن tbs\_db\_version. اشرحلي الكود بعد ما تكتبه. |

### قايمة مراجعة لكل ملف جديد

- [ ] كل استعلام فيه متغير بيعدّي على `$wpdb->prepare()`.
- [ ] كل مخرج للشاشة متعمله escape.
- [ ] كل معالج فورم فيه Nonce.
- [ ] كل إجراء أدمن فيه فحص صلاحية.
- [ ] مفيش `wp_` مكتوبة يدويًا، دايمًا `$wpdb->prefix`.
- [ ] كل نص ظاهر للمستخدم داخل `__( 'text', 'travel-booking-system' )`.
- [ ] مفيش استدعاء لدوال ACF (زي `get_field`).
- [ ] أول الملف: `defined( 'ABSPATH' ) || exit;`

### الأدوات

| الأداة | ليه |
| --- | --- |
| LocalWP | موقع ووردبريس تجريبي على جهازك مجانًا |
| Git + GitHub | نسخ احتياطية وتاريخ التغييرات |
| `WP_DEBUG` | يظهر الأخطاء وقت التطوير (في `wp-config.php`) |

**ما تجرّبش أبدًا على موقع عميل شغال.** استخدم LocalWP، وبعدين موقع Staging.

## 20. النشر على WordPress.org

### قبل ما ترفع

- **الرخصة:** GPLv2 أو أحدث، ومكتوبة في Header البلاجن وفي `readme.txt`.
- **الاسم والـ Slug:** `Travel Booking System` اسم عام جدًا وغالبًا مأخوذ أو قريب من أسماء موجودة. اختار اسم مميّز وتأكد إنه متاح قبل ما تتعلّق بيه. Prefix الدوال والكلاسات (`tbs_`) لازم يبقى مميّز برضو.
- **`readme.txt`:** وصف، تعليمات تثبيت، FAQ، Changelog، `Tested up to`، `Requires PHP`.
- **فحص Plugin Check:** يعدّي من غير أخطاء.
- **ممنوع:** كود مشفّر أو مخفي، طلبات لسيرفرات خارجية من غير توضيح للمستخدم، تتبّع من غير موافقة.
- **الترجمة:** Text Domain مطابق للـ Slug.

### المسار

1. ترفع الـ ZIP من صفحة رفع البلاجنات في WordPress.org.
2. فريق المراجعة يفحصه (بياخد من أيام لأسابيع)، وغالبًا هيطلب تعديلات في الأمان أو التسمية.
3. بعد الموافقة، بتستلم مستودع SVN وبتنشر النسخ منه.
4. كل تحديث: ترفع النسخة وتغيّر رقمها وتضيف Changelog.

### نصيحة

انشر **v0.4** على WordPress.org (بعد الاختبارات والـ Privacy). اشتغل قبلها على GitHub مفتوح، وجرّبها على موقع Rahal فعليًا. كده أول نسخة عامة تكون مستقرة، وأول تقييمات المستخدمين تبقى كويسة.

## 21. مثال: صاحب موقع هيستخدم البلاجن إزاي

**موقع Nile Trips عنده رحلات في CPT اسمه `trip`.**

**1. التثبيت:** يرفع البلاجن من Plugins > Add New ويفعّلها.

**2. الربط (مرة واحدة)** من Travel Bookings > Settings:

```text
Tour Post Type = trip
Seats Field    = capacity
Price Field    = price
Date Field     = trip_date
Currency       = EGP
Payment Instructions = ادفع في فرعنا في المنصورة خلال 48 ساعة
```

**3. العرض:** في صفحة الرحلة (أو Elementor Shortcode Widget):

```text
[tbs_available_seats]
[tbs_booking_form]
```

**4. تجربة العميل:**

```text
يدخل رحلة الأقصر → يشوف: متاح 12 مقعد
→ يختار 3 أفراد → الإجمالي يظهر
→ يكتب بياناته ويدوس احجز
→ يستلم رقم TB-2026-00001 وإيميل Booking Received
```

**5. شغل صاحب الموقع:** يفتح Travel Bookings، يلاقي الحجز Pending / Unpaid. العميل يدفع في الفرع، فيدوس Confirm + Mark as Paid. العميل يستلم إيميل التأكيد، والمقاعد تفضل محجوزة.

**6. لو العميل ما جاش:** بعد 48 ساعة المقاعد ترجع متاحة تلقائيًا (من v0.2 الحالة كمان بتتحول لـ Expired).

**7. لو العميل ألغى:** الأدمن يدوس Cancel، المقاعد ترجع فورًا.

## 22. الفلسفة وسجل القرارات

### الفلسفة

بنبني **Booking Engine قابل لإعادة الاستخدام**، مش بلاجن مخصوص لموقع واحد. Rahal هو أول موقع نجرّب عليه، مش آخر واحد.

أي قرار جديد لازم نسأل عليه:

> هل ده بيخدم الـ Architecture دي ولا بيربط البلاجن بموقع معين؟ وهل ده جزء من النسخة الحالية ولا بيأجّل نشرها؟

ولو الـ Architecture هتتغير، نحدّث الوثيقة الأول.
